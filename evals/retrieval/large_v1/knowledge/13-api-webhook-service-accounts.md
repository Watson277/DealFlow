Document status: current

## Developer Interfaces Scope and Eligibility

This business area brings together REST API Authentication, OAuth Client Credentials, Service Account Tokens. The grouping follows operational ownership and reader workflow; each subsection retains its own plan, version, status, limits, exceptions, and evidence.

| Topic | Capability state | Commercial scope |
|---|---|---|
| REST API Authentication | standard or plan-limited as stated | Plan-specific; see fact rule |
| OAuth Client Credentials | Dedicated-only capability | Enterprise and Dedicated |
| Service Account Tokens | standard capability | Business |

### REST API Authentication

The REST API accepts OAuth 2.0 client credentials for service accounts; interactive session cookies and basic authentication are rejected.

Applicability and contract treatment for machine authentication for server-to-server API calls. The controlling dimensions are the contracted edition, deployment model, data region, effective version, and recorded capability state. The catalog classification is standard or plan-limited as stated, with the commercial scope recorded as Plan-specific; see fact rule. A sales response may narrow that scope for a customer, but it may not silently broaden it. If an order form and this guide disagree, operations pauses activation and asks the tenant security administrator to resolve the discrepancy in writing.

Configuration workflow for machine authentication for server-to-server API calls. Customer Success opens the governing record before the setting is enabled, records the tenant and subscription, selects the authorized region, and links the approval. A second operator validates the resulting control in Virginia; production use begins only after the regional assurance workbook shows the expected value and a successful timestamp. The configuration is rechecked every 21 days and after any edition, identity-provider, network, or residency change that could alter eligibility.

Exception handling for machine authentication for server-to-server API calls. An exception must identify the precise unmet condition, the compensating control, an accountable owner, and an expiry no later than 35 days after approval. Renewal is a new decision rather than an automatic extension. A roadmap statement cannot serve as a compensating control, and a professional-services estimate does not prove that a capability is active. When the exception expires, the system either restores the documented baseline or disables the dependent workflow.

Operational verification for machine authentication for server-to-server API calls. The service samples the active setting every 6 hours while a change is open and compares it with the tenant registry. A mismatch creates a case for Customer Success, preserves the previous and proposed values, and blocks a compliance export from showing the control as passed. The result does not certify adjacent identity, logging, resilience, or integration controls that happen to use a similar term.

Evidence and auditability for machine authentication for server-to-server API calls. The customer package contains the regional assurance workbook, effective version, UTC activation time, approving role, last verification result, and any open exception. Tenant secrets, personal data, and raw customer content are redacted, but the plan, region, status, threshold, and unit remain visible. A screenshot without tenant and version context is supporting material only. Reviewers can determine whether the rule was current, historical, planned, custom, or unavailable at the time.

Failure and recovery for machine authentication for server-to-server API calls. If verification fails, new dependent operations stop while already committed records remain readable. The owner triages whether the cause is configuration drift, an expired entitlement, a regional restriction, or a version mismatch. Customer-impacting failures use the contracted support channel, and restoration requires a clean verification run plus approval from the tenant security administrator. Recovery does not reset a separate SLA, RTO, RPO, log-retention, or data-residency clock.

Customer responsibilities for machine authentication for server-to-server API calls. The customer supplies accurate tenant identifiers, maintains authorized contacts, and reports subscription or regional changes before relying on the control in production. Where the customer operates an external identity provider, key service, network appliance, integration platform, or on-premises component, its availability remains a customer dependency. DealFlow enforces the documented hosted boundary and produces the regional assurance workbook for the portion it operates.

A conforming procurement example is a tenant whose order form matches Plan-specific; see fact rule, whose control is activated in Virginia, and whose evidence package identifies the current version. The assessor accepts the result only for machine authentication for server-to-server API calls; the same package cannot be reused to claim a different capability. If the customer later moves to Sydney, the old verification remains historical evidence and a new regional check is required.

A non-conforming example is an implementation team citing a similarly named policy with a different number, lifecycle state, or subscription. Webhook signatures verify outbound events and cannot authenticate inbound API calls. The discrepancy is material even when both statements appear in official DealFlow documents, because the older or neighboring statement answers a different business condition. The response is corrected before proposal approval and the rejected interpretation remains in the audit trail.

Change management for machine authentication for server-to-server API calls. Material changes to eligibility, numeric limits, region coverage, or capability status are announced at least 90 days before they take effect unless an urgent security correction requires a shorter window. The notice names the old value, new value, affected subscriptions, migration action, and authoritative replacement document. Existing exceptions retain their original expiry but are reassessed against the new baseline. Historical text stays available for audit purposes and is marked superseded.
