## 发现的问题

1. 首次需求抽取连续三次约 180 秒超时，随后阶段正确标记 `FAILED`；调用 `/retry` 后第一次即成功。这是 GLM 上游稳定性问题，不是 Kafka 或 Worker 卡死。
2. 同一 RFP 上次抽取 76 条、本次抽取 88 条，而原文包含“以上四十一项要求”的描述。需求原子化规则存在非确定性和过度拆分，直接放大后续 LLM 调用数、Token 和耗时。
3. Proposal 摘要写“共 41 项要求”，但响应矩阵实际有 88 行，存在面向用户的数量口径不一致。
4. Capability 阶段首次 LLM 请求前约 32.7 秒，主要受 Reranker 冷启动影响；常驻预热可继续降低首任务延迟。

## 结论

`Capability=4` 和 `Proposal=3` 的受控并发均按设计工作，结果数量完整、顺序稳定、最终 Markdown 可访问。下一轮优化的优先级应为：需求抽取稳定性与合并规则、Reranker 启动预热、Proposal 总体章节输入压缩。
